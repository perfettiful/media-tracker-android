| Pod | Platform | One specific thing you learned from their demo/discussion | In your own words, how did the pod answer one of their platform-specific questions? |
| --- | -------- | --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Hunter Bammert-Mueller, Khalid Hassan, Danny King | React Native | React Native doesn't come with any icons. They rebuilt our Media Detail screen and the Dune cover is a book emoji, because there's no icon set out of the box. "Real icons, not emoji" was the first thing on their more-time list. Buttons needed manual styling too. I'd never thought about this since Compose just gives you `Icons.Filled.*` and pre-themed Buttons, I used a bunch of them without installing anything. RN hands you the pieces and you bring your own design system. | Q: JSX mixes markup and logic in one file, how does that compare to Compose's composables and which did you prefer? They said Compose. Their reasoning was that Compose is all just Kotlin, one language the whole way through, and JSX makes you switch between markup mode and code mode in the same file. Both put the UI and the logic together, but with Compose there's no second syntax to jump into, so you're not context switching. |
| Brian Willems + pod | Flutter | Assets work nothing like Android. Every image has to be listed by name in `pubspec.yaml`, one line each, and the extension and casing have to match exactly. That was their whole "what was hard" slide, png vs jpg tripping them up, which they admitted was self-inflicted bad naming. On Android you drop a file in `res/drawable` and it just works, there's no list to keep updated. | Q: Flutter draws every pixel itself instead of using native widgets, did you notice, did it feel native? They said they mostly noticed it while troubleshooting and reading docs, not while using the app. So the app itself didn't feel off to them. The seams showed up in the tooling and the documentation instead of in the UI. |
| Sadiq Ahmed, Ilyas Ibrahim, Nick Chyrklund | .NET MAUI | MAUI compiles down to real native controls, so the same code actually looks different depending on the OS. They showed one error, "Product name Apples already exists," coming out as a Windows modal on desktop and an iOS style alert on the phone. Same code, two different looking UIs. That's the opposite tradeoff from Flutter, which draws everything itself so it looks the same everywhere. | Q: MAUI targets more platforms than almost anything else, does write once run everywhere feel more or less real after trying it? Real enough to ship a business app, but with a list of asterisks. They said yes for cross platform business apps, steep setup but native performance once you're past it, one codebase for Windows, Mac and mobile. Then the catches: bugs inherited from Xamarin, thinner tooling, way fewer devs than RN or Flutter, waiting on Microsoft before you can use new native OS features, and desktop vs mobile fighting over one layout. |
| Jake Vigliotti, Dylan Browne | Ionic (Capacitor) | The web app in a shell thing costs you something real, and they had the screenshots. Same code side by side, browser vs Android emulator, and the phone version looked noticeably worse, cramped and unstyled next to the browser one. They said some features worked in the browser but rendered differently or failed outright on the emulator, and that CSS, images and dark mode were all inconsistent between the two. So you don't really get one target, you get two that mostly agree. | Q: How did state management in your web framework compare to Compose's state hoisting? They put the two next to each other. Compose hoists state, meaning a composable's state can live outside it and get passed in, which is why our Buttons take `onClick` and `enabled` as parameters. In Angular the state lives inside the class, their example was `incMedia()` doing `this.id++` and then calling `this.updateMedia()`. The component owns and changes its own state instead of getting it from a parent. |
| Kenan Port, Issa Ali, Ismail Bakkaoui, Samba Kamara | KMP (Kotlin Multiplatform) | Compose Multiplatform let them share the whole UI, not just the logic. I assumed KMP meant you share your models and rebuild the screens per platform, but their entire screen was in the shared folder. The only platform specific code was `getPlatform()` using `expect`/`actual`, which they described as a blank in shared code that each OS fills in. | Q: If shared logic is the appeal, what's the catch, what did you end up writing twice? Nothing, which wasn't the answer I expected. Their whole app lives in the shared folder and the one piece of per-platform code got generated by the setup wizard, they didn't write it. But they said the catch scales with the app, since saving files, networking and permissions all need per OS code that a small demo never hits. And they were all on Windows with no Mac, so they couldn't build or run the iOS side at all. The whole pitch is that it runs on both and they could only ever check one. |
| Fasika Yifru, Fuchee Young, Abdullahi Hassan | Progressive Web App (PWA) | The app part of a PWA is basically two files. `manifest.json` is what makes it installable, name and icons and standalone display, and `sw.js`, the service worker, is what makes it work offline. The service worker sits between the page and the network, catches every request, checks a cache first and only goes to the network if it misses. It also has to be served over https or the browser won't register it at all. | Q: No app store install and no SDK build step, what did you gain and what did you lose? Gained instant deploys with no review wait, you push to main and it's live, and there's no build or compile step at all. Lost device APIs and push notifications. They were also upfront that with no real backend there was no real data moving through it. Their tradeoff table added that you get no discoverability either, since there's no store listing for anyone to find. |
| Mai Moua's pod | Android TV (Compose for TV) | Losing touch changes which layouts are even possible, not just how you tap things. On a phone you can jump anywhere by tapping it, on a TV the d-pad walks focus one step at a time, so everything has to be reachable by stepping to it. They put it as everything must be d-paddable, keep everything connected. Their Search screen showed why: on screen keyboard you arrow around, horizontal rows instead of a vertical list, and a featured carousel, because scanning a long list with a remote is miserable. | Q: It's the same underlying Compose model, what carried over cleanly and what had to be rethought? They split it into two columns. Carried over was composables and modifiers, LazyColumn and LazyRow, and Material theming and layout, so the mental model and most of the API came along as is. Rethought was d-pad navigation, TV specific components instead of the mobile ones, and visual content and spacing. The spacing one is the one I wouldn't have guessed. It's not that the old spacing breaks, it's that you're sitting ten feet away so touch sized targets and phone sized text stop working. |
