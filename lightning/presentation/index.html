Part 2 - Standard Questions

Surprisingly easy?

  • Whole app is ~300 lines. Compose knowledge transferred, just renamed.
  • Dark mode, animations, and gestures were free.
  • Xcode previews render with fake data, the FakeMediaRepository trick.
The UI was the easy part. Everything from Compose transferred with new names: composables became View structs, StateFlow became @Published, LazyColumn became List. Dark mode, dynamic type, swipe gestures and list animations came from the platform for free. Previews run against an in-memory fake repository, the exact FakeMediaRepository trick from our Android app.

Part 2 - Standard Questions

Would we actually build with this?

  • For an iPhone-first product, yes. The pain is all in week one.
  • Nothing we wrote runs on Android. The frameworks look alike but share zero code.
  • Two platforms means two codebases. A budget question, not a preference.
// SwiftUI
List(todos) { TodoRow(item: $0) }

// Compose
LazyColumn { items(todos) { TodoRow(it) } }

// same idea. zero shared lines
Yes, for an iPhone-first product. The tooling pain is one-time, and past it SwiftUI is as productive as Compose with better system integration. But nothing we wrote ships to Android. The two frameworks rhyme, which makes a rewrite cheap, but it is still a rewrite. A real two-platform product means a cross-platform layer or two codebases and two budgets.

Part 3 - Platform Q&A - 1 of 4

How closely did @State/@Binding map onto Compose's state-hoisting model? Where did the mental model diverge?

  • @State is basically remember { mutableStateOf(...) }: a variable that updates the UI when it changes.
  • @Binding binds to someone else's @State. Think of it as a pointer to the original.
  • The divergence: Compose children get callbacks like onValueChange. Swift children just get a @Binding.
The state hoisting models are similar. The difference is how children receive state. In Swift a child takes a simple @Binding and writes through it. In Compose you pass the value down plus a callback like onValueChange to push changes back up.

Part 3 - Platform Q&A - 2 of 4

SwiftUI only targets Apple platforms. What did you gain or give up by being tied to one vendor's tooling?

ProsCons
Smooth developer experienceLocked to Apple
Ecosystem is seamlessMust develop on a Mac
Looks great with minimal effortCost
Once installed, Xcode just works. Previews are up the second you launch, and you can preview on iphones, ipads, and macs. Buttons and text fields look like an Apple app with zero effort. The tradeoffs: only Apple customers, you need a Mac to develop, and publishing costs about 99 dollars a year while Google Play is a one time 25.

Part 3 - Platform Q&A - 4 of 4

If you had to ship the same app on Android and iOS, what would you actually share vs. rebuild from scratch?

  • Share most of the backend: Kotlin for the API, validation, and other logic.
  • Rebuild the UI per platform in SwiftUI and Compose so it looks right on both.
  • Separate UIs let each app use unique platform features.
The backend logic does not need to change, and it is better if it does not. Devices have unique features, the iphone dynamic island, folding phones, different OS conventions. Building the UI separately lets each app take advantage of those while the product behaves the same everywhere.
